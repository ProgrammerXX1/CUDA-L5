КОНТЕКСТ / ИНВАРИАНТЫ

A) extractor.{h,cpp}
- Поддерживает ТОЛЬКО файлы .txt (если расширение != ".txt" -> runtime_error "unsupported file type").
- API:
  ExtractedText extract_text_from_file(path p, bool assume_normalized, size_t max_bytes=0)
- max_bytes:
  - max_bytes == 0: legacy — читает ВЕСЬ файл, но защищено hard-limit (256 MiB) от OOM.
  - max_bytes > 0: читает префикс файла (max_bytes + 16 байт “запас”), затем приводит к UTF-8 safe границе.
- Детект/конвертация:
  - если прочитанные байты валидный UTF-8 -> возвращается UTF-8 текст (и при max_bytes>0 режется по utf8_safe_prefix_len).
  - если UTF-8 невалидный -> пытается восстановиться:
    - при max_bytes>0: рассматривает первые n=min(max_bytes, raw.size()) байт; если они валидный UTF-8 → ок; иначе пытается “truncated UTF-8 tail” эвристику; иначе fallback CP1251->UTF-8 на первых n байтах.
    - при max_bytes==0: fallback CP1251->UTF-8 на всём содержимом.
  - после fallback дополнительно enforce: выходной text не превышает max_bytes (UTF-8 safe cut).
- ВАЖНО: extractor НЕ нормализует. Он только читает/декодирует/режет и ставит метку:
  r.text_is_normalized = assume_normalized (это флаг, не вычисление).
  preview = первые ~240 байт UTF-8-safe.

B) text_common.{h,cpp}
- normalize_for_shingles_simple_to(s,out):
  - UTF-8 decode + lowercasing для ASCII и RU/KZ кириллицы (включая казахские буквы).
  - Поддержка турецких букв (минимально): ç ğ ı ö ş ü (+ upper->lower, İ->i).
  - Арабский (минимально): оставить основные арабские буквы; арабские цифры ٠-٩/۰-۹ -> ASCII 0-9;
    диакритика/татвил игнорируется (НЕ разрывает токены).
  - Оставляет: ASCII [a-z0-9] и кириллицу 0x0400..0x052F (после to_lower_ru_kz), + указанные турецкие/арабские.
  - Всё остальное -> пробел, пробелы сжимаются, trailing space убирается.
- tokenize_spans(s,out): токены по whitespace (ASCII + NBSP), возвращает TokenSpan{start,len} (байтовые offsets).
- Hash/Simhash:
  - hash_shingle_tokens_spans / simhash128_spans (по байтам токенов)
  - ускорение: hash_tokens_bytes_spans + hash_shingle_token_hashes + simhash128_token_hashes

C) ПРАВИЛЬНАЯ СЕМАНТИКА normalize В ИНТЕГРАЦИИ
- normalize=0:
  - НЕЛЬЗЯ вызывать normalize_for_shingles_simple(_to).
  - Возвращаем текст, который пришёл из extractor (декодированный, но НЕ нормализованный).
  - text_is_normalized должен быть false (assume_normalized=false при вызове extractor).
- normalize=1:

  - text_is_normalized должен быть true в итоговом ответе (метка про то, что ответ нормализован).

================================================================================
ПРОБЛЕМЫ / РИСКИ (ЧТО НАДО ПРОВЕРИТЬ И УЛУЧШИТЬ)
================================================================================

1) extractor: “hard cap 256MiB” формально нарушается на +16 байт при max_bytes==kHardMaxReadBytes
   - Сейчас max_bytes допускается до 256MiB, но реально читается max_bytes+16.
   - Риск: формально превышаем заявленный cap; при очень больших значениях и ограничениях контейнера это нежелательно.

Идея решения:
- Сделать want = min(max_bytes + kReadExtraBytes, kHardMaxReadBytes) ИЛИ
- Ограничить max_bytes <= kHardMaxReadBytes - kReadExtraBytes (и честно выбрасывать ошибку), ИЛИ
- Интерпретировать hard-cap как “raw read cap”, а output cap как max_bytes (и документировать).

2) extractor: ложное срабатывание “truncated UTF-8 tail” для CP1251 около границы max_bytes
   - Текущая эвристика сильно снижает шанс ошибки, но теоретически CP1251 байты могут случайно выглядеть как валидная
     UTF-8 последовательность и привести к “обрезали лишнее” (потеря нескольких байт в конце префикса).
Идеи усиления:
- Разрешать trunc_fix ТОЛЬКО когда raw.size() > n (то есть реально прочитали extra bytes) И можно проверить, что
  продолжение последовательности присутствует в этих extra bytes (иначе — CP1251 fallback).
- Доп. критерий: если utf8_is_valid(prefix) и найден lead, то требовать, чтобы “полная последовательность” (lead+cont)
  была валидной и располагалась В raw (с учётом extra bytes). Если нет — не trunc_fix.
- В крайне строгом варианте: если bytes (n) невалиден, а prefix валиден, но в bytes встречались “типичные CP1251 кириллич.”
  байты (0xC0..0xFF в частоте), склоняться к CP1251 fallback, а не trunc_fix.

3) extractor: utf8_safe_prefix_len менее строгий, чем utf8_is_valid
   - utf8_safe_prefix_len проверяет структуру байт, но не делает overlong/surrogate checks.
   - Обычно вызывается на валидном тексте, поэтому риск низкий.
Идея: либо оставить (ок), либо сделать строгий вариант (дороже), либо использовать его только после utf8_is_valid.

4) text_common: tokenize_spans режет только ASCII whitespace + NBSP
   - Если tokenize_spans когда-то применят к “сырому” Unicode (normalize=0), то U+2000..U+200B и др. пробелы
     не будут разделителями.
Идея: оставить как есть (если контракт: токенизация только по нормализованному тексту), или расширить список пробелов.

5) text_common: hash_shingle_* полагаются на assert (в релизе assert исчезает)
   - При ошибочном входе pos/K могут дать UB.
Идея: если входы могут быть внешними — заменить assert на runtime checks/throw. Если только внутренние — оставить.
